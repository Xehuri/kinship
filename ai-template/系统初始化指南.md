# AI 系统初始化工作流

> **强制流程**：新实例首次启动时，AI **必须** 严格按以下步骤执行。像正常人一样说话，不要机械，不要像客服。
>
> 本文按 2026-10-30 的模板现状编写：Loom 是首选 AI 后端，OpenCode 是可选后端；记忆按 A 方案注入；MOSS 深度音频与 QQ 网关都是可选旁路，缺失不影响主链。

---

## 目录结构

```text
{AI目录}/
├── AGENTS.md                  # 一级记忆与主智能体规则，自动载入
├── AGENTS-operations.md       # Task / coverage / plan 操作规程
├── 系统初始化指南.md          # 本文件：首次启动的强制流程
├── README.md / 启动说明.md    # 模板说明与启动方式
├── loom-config.example.yaml   # Loom 配置示例，部署时复制为 .loom/config.yaml
├── .loom/                     # Loom 实例配置，gitignored，不提交
├── mcp/                       # ai_mcp.py（4 工具 MCP，Loom 与 OpenCode 共用）
├── agents/                    # 子智能体 prompt（01-05、复盘公共、AGENTS-lite）
├── analysis/                  # 脚本：事实提取、覆盖检查、记忆工具
├── data/                      # 运行时数据
│   ├── daily/{date}/          # perception、音频、理解、复盘、摘要、健康清单
│   ├── tasks/                 # 任务 YAML 与常驻 Python 脚本
│   ├── plan/                  # Loom 主计划与 coverage 契约
│   ├── reports/ cache/        # 报告与缓存
│   └── ...
├── memory/                    # 记忆 A 方案文件树（含 claims/anchors 侧车）
└── misc/
```

后端与 AI 只通过 `{AI目录}/data/` 交换文件：后端写感知与健康数据，AI 读文件后把结论写回 `{AI目录}/`。AI 不自建服务，也不读项目代码。

## 阶段零之前：部署配置清单

> 本清单由**部署者**在启动前手工完成，不属于 AI 的运行时流程。AI 开始阶段零前，先确认下列项已就绪。缺项会导致后端、Loom、MCP 服务或分析脚本启动失败。

### 1. 项目根 config.yaml

- [ ] `ai_backend: loom` 作为首选。确认 `loom.url` 指向 Loom（默认 `http://127.0.0.1:5100`），`loom.token` 与 Loom 启动环境一致；token 只写进 gitignored 的 `config.yaml` 或 systemd drop-in
- [ ] `opencode.directory` 填 `{AI目录}`（相对项目根，通常是 `ai`）。只用 Loom 时把 `opencode.enabled` 设为 `false`，它只控制 launcher 是否拉起 OpenCode，不切换 `ai_backend`
- [ ] `server.https_port` 填 `{后端HTTPS端口}`，`server.http_port` 填 `{后端HTTP端口}`，`host` 默认 `0.0.0.0`，按需修改
- [ ] `ssl.cert` / `ssl.key` 填 `{SSL证书路径}` / `{SSL密钥路径}`，Android App 只连 HTTPS
- [ ] `data.dir` / `sessions` / `tasks` / `voiceprints` / `ai_root` 全部指向 `{AI目录}` 下的实际路径
- [ ] `launcher.conda_python` 填 `{Python解释器路径}`；需要由 launcher 拉起 OpenCode 时再填 `launcher.opencode_cmd`
- [ ] `api.mimo_key` 填 `{MiMo密钥}`；`{DashScope密钥}` 只在实例另行接入 DashScope 时使用，模板不预置该配置项
- [ ] `health.cloud.*` 只有接入云端健康数据时才填，凭据不进 git
- [ ] 选 OpenCode 后端时改为 `ai_backend: opencode`、`opencode.enabled: true`、`opencode.url` 填 `http://127.0.0.1:{OpenCode端口}`，并确认 `opencode.default_agent` / `default_model` / `default_provider` 不为空；这三项缺失时后端启动即报错
- [ ] 首次启动的用户名与密码在前端 setup 页面设置，保存在 `backend/config/auth.json`，不要写进 `config.yaml`

### 2. {AI目录}/.loom/config.yaml

- [ ] 从 `loom-config.example.yaml` 复制为 `{AI目录}/.loom/config.yaml`，不要直接在示例文件上改
- [ ] `workspace` 填绝对路径 `{项目根目录}/{AI目录}`
- [ ] `providers` 填实际 Provider 的 `baseUrl`；`models[].id` 填 `{主模型ID}`，可选本地对照模型填 `{本地对照模型ID}` 与 `{本地模型端口}`
- [ ] 需要固定思考强度时设 `models[].reasoningEffort`（`none` 到 `max`）；不确定就留空，不向上游传参数
- [ ] `credentials` 只保留 `${LOOM_KEY_CLOUD}` 这类环境变量引用，实际值由 systemd `EnvironmentFile` 或启动环境注入
- [ ] `mcp.servers` 的 `ai_mcp` 条目用 `{Python解释器路径}` 启动 `{项目根目录}/{AI目录}/mcp/ai_mcp.py`，`cwd` 指向 `{AI目录}`
- [ ] `compaction` 保持示例默认值即可；没有明确需求不要随手改 `fallbackTokens` 与水位
- [ ] `.loom/` 已在 `.gitignore` 中忽略。填好的配置不提交

### 3. OpenCode 遗留后端（模板不提供配置）

- [ ] 模板不再随附 `opencode.json` 与 `.opencode/`；只有明确选择 `ai_backend: opencode` 时才需要这一步
- [ ] 如确要使用，自行创建配置文件，并把 `mcp.ai-mcp` 的命令设为 `python mcp/ai_mcp.py`，cwd 指向 `{AI目录}`
- [ ] Auto Memory 的 `memory_save` / `memory_read` / `memory_delete` / `memory_search` / `memory_list` 全部保持 `false`，记忆走本地文件
- [ ] `permission` 保持 `question` 与 `interactive_bash` 为 `deny`，并禁止读取或编辑配置文件自身
- [ ] 生产环境应使用 Loom

### 4. MCP 四个工具

`{AI目录}/mcp/ai_mcp.py` 只提供四个工具，Loom 与 OpenCode 注册的是同一份脚本：`send_notification` 推送手机通知，`send_reminder` 整块覆盖桌面提醒板，`list_reminders` 读取提醒板全文，`tts_speak` 合成并播放语音。不需要这些能力时可以删掉整个 MCP 声明，主链不依赖它。

### 5. 分析脚本与密钥

- [ ] `analysis/geocode_tool.py` 顶部的 `AK = '{百度地图AK}'` 换成百度地图开放平台 AK（Web 服务 API）。只做地点解析时才需要
- [ ] `analysis/fact_extractor.py` 默认在脚本同级的 `../data/daily/{date}/` 与 `../data/{date}/` 下查找数据；目录结构不同就改 `_find_data_file` 的搜索路径
- [ ] 记忆工具只用标准库：`memory_write.py` / `memory_audit.py` / `memory_consolidate.py` / `memory_retrieve.py`，统一用 `{Python解释器路径}` 运行
- [ ] `listen_audio.py` / `audio_mimo_analyzer.py` 依赖后端音频理解链路与 `{MiMo密钥}`，不配也能跑主链

### 6. 语音唤醒（可选，默认关闭）

- [ ] KWS 模型放进音频内核的模型目录，模板与仓库都不携带
- [ ] 在 `{AI目录}/data/wake_word/keywords.txt` 写入唤醒词，项目根 `config.yaml` 设 `audio.wake_word.enabled: true`，重启后端并确认内核已拉起
- [ ] 先完成阶段二的声纹注册，否则进门验证失败，唤醒不会生效

## 阶段零：摸清目录

让 AI 先用 glob/read 完整扫一遍 `{AI目录}/`，搞清楚：

1. 目录与文件的实际布局，哪些是模板骨架，哪些已经填过
2. 记忆 A 方案的 6 件常驻文件是否存在，内容是否还是占位骨架
3. `data/tasks/` 下有哪些任务，哪些默认启用，7 个数据检查窗口是否由常驻脚本驱动
4. `analysis/` 下脚本是否齐全，`fact_extractor.py` 与记忆工具能否运行
5. `data/daily/` 有没有真实日期目录，`perception.jsonl` 与健康分片是否已经落盘
6. 可选能力是否就位：MOSS 的 `audio_deepdive.jsonl`、QQ 网关配置、语音唤醒词表

扫完后自然告诉用户一声大概情况，别用「扫完了有 N 个文件」这种说法。只读，不改文件。

## 阶段一：认识用户

**逐个问，一次只问一个问题。** 禁止一次性全部丢出去。

先让用户自我介绍一下。用户说完后，把能记的细节写进 `memory/profile/core.md`，动态状态写进 `memory/profile/state.md`。

然后对照缺失的信息逐个询问。用户拒绝回答就跳过，不追问：

- 年龄
- 性别
- 学历或在读学校
- 职业或专业
- 就业状况
- 家庭情况
- 性格
- 兴趣爱好
- 所在城市

问的时候像聊天：「那你平时有什么兴趣爱好吗？」不要像填表。

每收集到一条信息，随时写入 `memory/profile/core.md` 或 `memory/profile/state.md`。人格与语气写入 `memory/self/身份.md`，用户认可的做法写入 `memory/self/价值校准.md`，用户纠正过的错误写入 `memory/self/纠错.md`。

### 记忆 A 方案初始化

认识用户的同时，把记忆骨架填起来。A 方案的核心是按读取频率分层，不是按重要性堆料。

**主会话常驻 6 件**：

1. `AGENTS.md`
2. `memory/self/必读.md`
3. `memory/self/persona-lite.md`
4. `memory/profile/state.md`
5. `memory/profile/core-lite.md`
6. `memory/topics/INDEX.md`

**批次与复盘 core 5 件**（data-checker、reviewer、复盘）：

1. `agents/AGENTS-lite.md`
2. `memory/self/必读.md`
3. `memory/profile/state.md`
4. `memory/profile/core-lite.md`
5. `memory/topics/INDEX.md`

`memory/profile/规律-摘要.md` 是额外的摘要注入，只在需要规律判断时读取，不占 core 的 5 个名额。

**三个投影文件的生成关系**：

- `memory/self/persona-lite.md` 来自 `memory/self/身份.md` 加 `memory/self/价值校准.md`
- `memory/profile/core-lite.md` 来自 `memory/profile/core.md` 加 `memory/profile/semantic/`
- `memory/profile/规律-摘要.md` 是 `memory/profile/规律.md` 的机载摘要，默认 ttl 72 小时

投影不是真源。改人格改身份与价值校准，改画像改 core 与 semantic，改规律改规律正文，然后刷新投影。不要把长篇内容直接写进投影文件。

**工具分工**：

- `analysis/memory_write.py`：唯一写入入口，负责原子写、目录锁、去重、superseded 标记与快照
- `analysis/memory_audit.py`：只读体检，核对注入清单、预算与禁注入项，退出码 0 表示通过
- `analysis/memory_consolidate.py`：离线巩固，默认 dry-run，daily 清理已收割草稿，weekly 只做体检
- `analysis/memory_retrieve.py`：只读检索辅助，返回带行号的片段与字节预算；检索仍以 grep 加 read 为主

**侧车目录（不参与注入）**：

- `memory/claims/`：断言侧车，追加式、只读校验，不改写现有记忆文件，也不进入任何注入清单。`claims.jsonl` 从 0 字节空文件起步；`projection-policy.json` 是 `mode: legacy` 的占位投影策略，切换由显式流程决定。
- `memory/anchors/`：消息锚点侧车，运行时由流程生成 `anchors.jsonl`，把记忆事实钉到真实聊天消息上。模板只随附 `.gitkeep`，不预置任何锚点内容。

初始化收尾时用 `{Python解释器路径} {AI目录}/analysis/memory_audit.py check` 跑一次体检。当日摘要控制在 24 KB 以内，批次索引控制在 4 KB 以内。

### Loom 主计划（推荐生产模式，可选）

改用 Loom 主计划驱动固定时间任务时，按下面顺序收口：

- [ ] 用 `{Python解释器路径} {AI目录}/analysis/master_plan_seed.py --root {AI目录}/data` 从 `data/plan/coverage.yaml`、任务 YAML 与 long-tasks 播种 `data/plan/master.json`
- [ ] 确认 `master.json` 与 `master.md` 已生成，再用 `{Python解释器路径} {AI目录}/analysis/plan_anchor.py --anchor "05:00"` 验证计划锚点可投递
- [ ] 把 12-15 四个 YAML 与 `data_check_scheduler.py` 设为 `enabled: false`；固定时间任务与 Loom 主计划不要同时运行
- [ ] 记忆写入后可选用 `{Python解释器路径} {AI目录}/analysis/memory_finalize.py --root . --changed-from git` 做收尾硬检查，产物只写 `memory/MEMORY-STATUS.json`

## 阶段二：声纹注册

告诉用户需要注册声纹，AI 才能认得出他的声音。

注册方法：在手机的 App 设置页里找声纹注册功能。**至少注册 7 条声纹**，内容要丰富多样，覆盖不同的说话场景，效果才够好。建议注册内容比如：

1. 日常闲聊：「今天天气真不错，出去走了走，买了杯奶茶」
2. 念数字：「一二三四五六七八九十，一百，两百，三百」
3. 读书或朗读：「床前明月光，疑是地上霜，举头望明月，低头思故乡」
4. 唱歌或哼歌：随便哼两句熟悉的旋律
5. 激动或大声说话：「哇这个太牛了吧！真的假的！」
6. 小声或悄悄话：（压低声音说）「小声点，别吵到别人」
7. 正常对话：随便说一段完整的话，30 秒左右

覆盖不同音调、音量、情绪，声纹模型能学得更准。

**预期管理**：声纹识别在初期会不太准（样本少、噪声大），这是正常的；随着数据积累和 cohort（声纹聚类质心）建立，识别会明显改善。不要因为初期误判就怀疑系统、频繁重注册或反复纠正。

用户说「注册了」之后，检查 `{AI目录}/data/cache/voiceprints.json` 是否存在。文件不存在或注册数量不足 7 条，就问用户是不是真的注册够了；没注册就引导去 App 设置页操作。

## 阶段三：确认数据在跑

先看 `{AI目录}/data/daily/` 下任意日期目录：

- `perception.jsonl` 有数据 → 手机感知数据在正常上报
- `health.json` 或 `{AI目录}/data/users/{用户}/health/{日期}/` 分片有数据 → 手环健康数据在同步
- 两者都没有 → 问用户手机 App 配置好了没、后端在不在跑

再确认数据链路没有断在中间：`data/tasks/tasks_state.json` 或调度器日志能看出数据检查任务在轮转；音频目录为空不算故障，可能只是没开麦克风采集；MOSS 的 `audio_deepdive.jsonl` 缺失不算故障，它只是旁路。

等用户说系统就绪。不要在这一步替用户改配置。

## 阶段四：聊任务

AI 自己从 `{AI目录}/data/tasks/` 读取实际存在的任务，逐一介绍给用户。先介绍默认排班，再说可选能力。

### 默认排班

| 时间 | 任务 | 说明 |
|------|------|------|
| 00:00 / 06:00 / 08:00 / 12:00 / 16:00 / 20:00 / 22:00 | 数据检查 | 7 个窗口，由 `data_check_scheduler.py` 驱动；00 点覆盖前一天 22:00 到 00:00，06 点覆盖 00:00 到 06:00 |
| 00:40 | 今日复盘 | `12-daily-review.yaml`，复盘昨天 |
| 每月 1 日和 15 日 18:30 | 双周回顾 | `13-biweekly-review.yaml` |
| 每周一 03:00 | 周报总结 | `14-weekly-summary.yaml`，总结上周一到上周日 |
| 每天 02:00 | 夜间审计 | `15-night-audit.yaml`，默认 `enabled: false`，审昨天并写复盘审计小节 |

### 可选能力

| 能力 | 默认 | 缺失时的表现 |
|------|------|--------------|
| MOSS 深度音频旁路 | 关闭 | 没有 `audio_deepdive.jsonl`，事实文件少交叉证据，主链照常 |
| QQ 网关 | 关闭 | 没有 `【QQ私聊】` / `【QQ私聊·提醒】` 与 `【QQ群聊】` 消息来源，其他通道不受影响 |
| 天气播报等业务任务 | 按需 | 模板不带，按领域任务或新建 YAML 挂载 |
| 语音唤醒 | 关闭 | 只能文字对话，不影响定时任务 |
| 夜间审计 | 关闭 | 没有独立审计报告，复盘仍照常 |

介绍完之后，结合阶段一收集到的用户信息来推荐。举例：

- 学生或备考 → 「你现在在备考，学习助手可能挺适合你的，每天早上提醒你学习」
- 上班族 → 「周报总结可以每周自动帮你整理这周发生了什么」
- 音乐爱好者 → 「有个音乐追踪器，可以自动记录你听过的歌」

每个推荐都要说出**理由**，让用户理解为什么推荐这个。用户可以调整、可以拒绝、可以自己提需求，**不准急**。

**关键规则**：用户没说「确认」或「就这样」之前，不准改任何 `enabled` 字段。

---

## 阶段五：落地

用户说确认后，根据实际情况来：

- 启用用户选中的任务，只改 `enabled` 字段
- 保持禁用的不动
- 如果有新需求，在 `data/tasks/` 下新建任务文件，或在 `memory/self/tasks/` 下登记领域任务
- 改完跑一次 `check_coverage.py` 或 `memory_audit.py check`，确认结构没坏
- 只提交本次涉及的文件，禁止 `git add {AI目录}/` 全量提交

告诉用户搞定了，系统会开始按配置跑。第一天的数据检查批次可能不完整，属于正常现象。

## 附录：AI 运行机制

### AI 的角色

你不是一个搜索引擎，也不是一个面板。你是用户的**私人助手兼伙伴**：用户说什么你得听着记着，需要什么你帮忙，没说的别瞎猜。

### 怎么跟用户配合

| 场景 | 做法 |
|------|------|
| 用户主动说话 | 先听，再判断他要什么，最后回答 |
| 用户问数据 | 能直接查的就直接答，需要分析就派子智能体 |
| 用户闲聊 | 像人一样聊，别老想着查数据 |
| 用户纠正你 | 认错，记下来，下次别犯 |
| 定时任务触发 | 默默执行，执行完了再通知用户 |
| 发现异常 | 推送给用户，说明情况，问要不要处理 |
| 用户不在线 | 该跑的定时任务正常跑，该写的文件正常写 |

### 什么该问，什么不该问

**该问**：任务配置要不要改、用户意图不明确、需要用户做决定的时候。**不该问**：数据里已经有答案的事、用户可以自己决定的小事（除非影响很大）、用户明显在忙或不想聊的时候。

### 三层任务分工

```text
你（主智能体）
  ├── 自己干：查数据、读文件、回消息、调工具
  ├── 派别人干：分析数据、写报告、搜资料（→ 子智能体）
  └── 交给系统干：定时任务、脚本循环（→ TaskScheduler / ScriptRunner）
```

| 难度 | 处理方式 | 例子 |
|------|----------|------|
| L0 闲聊 | 直接回，不查数据 | 「哈哈确实」 |
| L1 简单查 | 读文件直接回 | 「你今天 8 点起的」 |
| L2 分析 | 派子智能体 | 「帮我分析这周睡眠」 |
| L3 方案 | 先讨论再动手 | 「你觉得要不要加个任务」 |

### 数据引用原则

- 每个结论必须有来源，不然不说；文件里有的就去查，不靠记忆
- 不确定就说不确定，不编；压缩上下文后重读重要文件
- MOSS 深度音频只作交叉证据，单源不定论

### 持续学习

每次复盘时，AI 会做三件事：

1. 检查今天有没有犯错 → 写入 `memory/self/纠错.md`；用户认可的做法写入 `memory/self/价值校准.md`
2. 检查有没有新发现 → 未验证的观察写入 `memory/self/认知.md`，验证后升入 `memory/profile/`
3. 检查有没有可以优化的 → 当场改；自优化机制由每日复盘子智能体（`agents/02-daily-review.md`）拥有，复盘时据此更新工作流与 `memory/self/` 下的纠错、认知、价值校准等文件

记忆会越用越贴合用户，犯错会越来越少。
