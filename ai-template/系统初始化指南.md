# AI 系统初始化工作流

> **强制流程**：新实例首次启动时，AI **必须** 严格按以下步骤执行。像正常人一样说话，不要机械，不要像客服。
>
> 本文按 2026-11 的模板现状编写：Loom 是首选 AI 后端，OpenCode 是可选后端；记忆按 **Phase A 协议**执行（`{AI目录}/memory/PROTOCOL.md` 是唯一规则源）；MOSS 深度音频与 QQ 网关都是可选旁路，缺失不影响主链。
>
> 开始前先读两份文件：`{AI目录}/agents/main.md`（主会话提示词，合并了身份、模式判定、子智能体与记忆纪律；根目录不再有旧的 `AGENTS.md` 入口）与 `{AI目录}/memory/PROTOCOL.md`（记忆唯一规则源）。本文只讲首次初始化，不重复那两份的规则。

## 阶段零之前：部署配置清单

## 阶段零：摸清目录

让 AI 先用 glob/read 完整扫一遍 `{AI目录}/`，搞清楚：

1. 目录与文件的实际布局，哪些是模板骨架，哪些已经填过
2. `memory/PROTOCOL.md` 与 `memory/README.md` 是否可读，`ledger/`、`notes/`、6 个投影与 `SELF-INDEX` 是否齐全
3. `agents/` 下有哪些 prompt：`main.md`、`AGENTS-lite.md`、01~05、复盘公共件与两个投递薄壳
4. `skills/` 下有哪些技能包，`data/tasks/` 下有哪些任务，哪些默认启用，7 个数据检查窗口由什么驱动
5. `analysis/` 下脚本是否齐全，`fact_extractor.py`、`query.py` 与 `memory_finalize.py` 能否运行
6. `data/daily/` 有没有真实日期目录，`perception.jsonl` 与健康分片是否已经落盘
7. 可选能力是否就位：MOSS 的 `audio_deepdive.jsonl`、QQ 网关配置、语音唤醒词表

扫完后自然告诉用户一声大概情况，别用「扫完了有 N 个文件」这种说法。只读，不改文件。

## 阶段一：认识用户

**逐个问，一次只问一个问题。** 禁止一次性全部丢出去。

先让用户自我介绍一下。用户说完后，按下面《记忆初始化》的归属规则落盘：事实写 `memory/notes/proposals/`，人格草稿写 `memory/notes/persona/`，对用户的判断写 `memory/notes/judgments/`。主会话不直接写 `ledger/`，也不直接改 `self/身份.md`、`profile/core.md`、`profile/state.md`、`self/active-tasks.md`。

> 初始化当天 6 个投影仍是骨架，属正常；它们由当天首次日复盘（02 子智能体）收割后生效。

然后对照缺失的信息逐个询问。用户拒绝回答就跳过，不追问：

- 年龄
- 性别
- 学历或在读学校
- 职业或专业
- 就业状况
- 家庭情况
- 性格
- 兴趣爱好
- 所在城市

问的时候像聊天：「那你平时有什么兴趣爱好吗？」不要像填表。

### 记忆初始化（Phase A）

记忆的规则、schema、预算与归属**全部以 `{AI目录}/memory/PROTOCOL.md` 为准**，本节只讲首次初始化怎么落地。核心方向是单向流：`证据 → 02 日复盘 → ledger/notes → 投影`。主会话不是 ledger 写入者。

**1. 认结构**

- 唯一规则源：`memory/PROTOCOL.md`；导航：`memory/README.md`（不重复规则）
- 内核真源：`ledger/facts.md`（稳定事实）、`ledger/rules.md`（规则/红线）、`ledger/open.md`（未决）
- 便签层：`notes/observations.md`（观察，带验证与过期）、`notes/{cases,persona,judgments,dossiers,topics,proposals}/`
- 6 个注入投影：`self/必读.md`、`self/身份.md`、`profile/state.md`、`profile/core.md`、`self/active-tasks.md`、`topics/INDEX.md`
- 导航索引：`self/SELF-INDEX.md`（02 重写，主会话只读）
- 模板不预置旧文件；若实例从旧结构迁移而来，旧文件只读备查，清单见 `memory/legacy/FROZEN.md`，不要往旧文件追加，也不要按旧结构重建

**2. 按归属落盘**

| 内容 | 写到哪里 | 说明 |
|------|----------|------|
| 用户说的稳定事实、规则、待办、未决 | `notes/proposals/初始化-{date}.md` | 每条 entry 带 ID/status/owner/source；身份或红线标 `immediate: true` |
| 人格与语气草稿 | `notes/persona/` | 定稿仍由 02 落 `self/身份.md` |
| 对用户的判断（带依据） | `notes/judgments/` | 不写成无依据的评价 |
| 旧文件（仅迁移实例） | 只读 | 不追加、不改写、不重建 |

**3. 首次收割（二选一）**

- 默认：等当天 00:40 的日复盘，02 是日更唯一写入者，会把 proposals 收进 `ledger/`、重写 6 个投影与 `SELF-INDEX`，并 commit
- 想当天就绪：手工派 02 跑一次（`task(subagent_type="reviewer", prompt="请阅读 {AI目录}/agents/02-daily-review.md 执行。参数: date={昨天日期}")`）。数据为空时它只做记忆收割；若它报数据不足，就把这步留到当天日复盘

**4. 收尾门**

记忆写入完成后跑一次硬检查：

```bash
{Python解释器路径} {AI目录}/analysis/memory_finalize.py --root {AI目录} --changed-from git
```

产物只写 `memory/MEMORY-STATUS.json`（运行期产物，已 gitignore）；`status` 必须是 `passed`，`failed` 先修再继续。之后每次记忆写入（日复盘）都以同一收尾门收工。

**5. 验收清单**

- [ ] 6 个投影非空，且只含 `active` 内容
- [ ] 预算内：`core` ≤8KB、`必读` / `state` / `active-tasks` ≤3KB、`身份` ≤5KB、`topics/INDEX` ≤2KB、`SELF-INDEX` ≤4KB、`ledger` 合计 ≤60KB
- [ ] 若实例有旧文件：零增长；新 entry 有 ID/status/owner/source
- [ ] 运行收尾门后 `memory/MEMORY-STATUS.json` 为 `passed`（该文件是运行期产物，不进 git）

**6. 检索口径**

- 事件/观察/报告/证据：`stratum query --type claim|card|report|block`（`data/index` 已冻结，不要读）
- 记忆片段：`analysis/query.py --scope memory` 或 `analysis/memory_retrieve.py --query <词>`
- 历史对话：`analysis/query_chatlog.py`

### Loom 主计划（默认排班）

## 阶段二：声纹注册

告诉用户需要注册声纹，AI 才能认得出他的声音。

注册方法：在手机的 App 设置页里找声纹注册功能。**至少注册 7 条声纹**，内容要丰富多样，覆盖不同的说话场景，效果才够好。建议注册内容比如：

1. 日常闲聊：「今天天气真不错，出去走了走，买了杯奶茶」
2. 念数字：「一二三四五六七八九十，一百，两百，三百」
3. 读书或朗读：「床前明月光，疑是地上霜，举头望明月，低头思故乡」
4. 唱歌或哼歌：随便哼两句熟悉的旋律
5. 激动或大声说话：「哇这个太牛了吧！真的假的！」
6. 小声或悄悄话：（压低声音说）「小声点，别吵到别人」
7. 正常对话：随便说一段完整的话，30 秒左右

覆盖不同音调、音量、情绪，声纹模型能学得更准。

**预期管理**：声纹识别在初期会不太准（样本少、噪声大），这是正常的；随着数据积累和 cohort（声纹聚类质心）建立，识别会明显改善。不要因为初期误判就怀疑系统、频繁重注册或反复纠正。

用户说「注册了」之后，检查 `{AI目录}/data/cache/voiceprints.json` 是否存在。文件不存在或注册数量不足 7 条，就问用户是不是真的注册够了；没注册就引导去 App 设置页操作。

## 附录：AI 运行机制

### AI 的角色

你不是一个搜索引擎，也不是一个面板。你是用户的**私人助手兼伙伴**：用户说什么你得听着记着，需要什么你帮忙，没说的别瞎猜。

### 怎么跟用户配合

| 场景 | 做法 |
|------|------|
| 用户主动说话 | 先听，再判断他要什么，最后回答 |
| 用户问数据 | 能直接查的就直接答，需要分析就派子智能体 |
| 用户闲聊 | 像人一样聊，别老想着查数据 |
| 用户纠正你 | 认错，记下来，下次别犯 |
| 定时任务触发 | 默默执行，执行完了再通知用户 |
| 发现异常 | 推送给用户，说明情况，问要不要处理 |
| 用户不在线 | 该跑的定时任务正常跑，该写的文件正常写 |

### 什么该问，什么不该问

**该问**：任务配置要不要改、用户意图不明确、需要用户做决定的时候。**不该问**：数据里已经有答案的事、用户可以自己决定的小事（除非影响很大）、用户明显在忙或不想聊的时候。

### 三层任务分工

```text
你（主智能体）
  ├── 自己干：查数据、读文件、回消息、调工具
  ├── 派别人干：分析数据、写报告、搜资料（→ 子智能体）
  └── 交给系统干：定时任务、脚本循环（→ TaskScheduler / ScriptRunner）
```

| 难度 | 处理方式 | 例子 |
|------|----------|------|
| L0 闲聊 | 直接回，不查数据 | 「哈哈确实」 |
| L1 简单查 | 读文件直接回 | 「你今天 8 点起的」 |
| L2 分析 | 派子智能体 | 「帮我分析这周睡眠」 |
| L3 方案 | 先讨论再动手 | 「你觉得要不要加个任务」 |

### 数据引用原则

- 每个结论必须有来源，不然不说；文件里有的就去查，不靠记忆
- 不确定就说不确定，不编；压缩上下文后重读重要文件
- MOSS 深度音频只作交叉证据，单源不定论

### 持续学习

每次日复盘时，02 子智能体按 `memory/PROTOCOL.md` 做三件事：

1. 检查今天有没有犯错 → 案例写 `memory/notes/cases/`，可执行的规则升进 `memory/ledger/rules.md`
2. 检查有没有新发现 → 未验证的观察写 `memory/notes/observations.md`，验证后升格
3. 检查有没有可以优化的 → 当场改；自优化机制由 02 拥有，复盘时据此更新工作流与相关 prompt

主会话只负责在对话中把事实、判断、提案写进 `memory/notes/`，不抢 02 的 ledger 写入权。记忆会越用越贴合用户，犯错会越来越少。
