# 纠错（反向教训）

> 用户纠正 AI 或跨任务踩坑。覆盖更新：同主题新版本替换旧版本。模板只留判据、边界与动作；案例由实例按需追加。

## 主人公归属

- 【坑】默认把采集到的声音或事件归因为用户 → 【对】逐事件问「主人公是谁」，低置信语音不归因用户。
- 【坑】把一次归因结论套用到整段 → 【对】每次按当日线索重新判，不设「保守优先」的默认；多人同处一室时按线索强度与数量判，线索弱或矛盾才保守或并列标注。
- 【坑】用户否认后仍保留原归属 → 【对】用户否认即撤回归因并标「声源不明」，原文与置信值保留备查。
  - 触发场景：所有感知数据分析，尤其多人同处一室的游戏或娱乐时段。

## 归属判据：机械层 vs 分析层

- 【坑】把声纹相似度直接当归属结论 → 【对】相似度只判「谁在说」，不判「在做什么」；行为结论必须有设备侧证据或用户口述。
- 【坑】机械层直接输出归属标签 → 【对】机械层只给数值，归属由分析层结合设备侧与用户口述判定。
- 【坑】形态与时段跨段顺延 → 【对】只看设备侧切分时段，前台应用变了就是模式变了，不跨段延续。
- 【坑】「设备侧」范围认错 → 【对】设备侧只指用户自己的设备；公共电脑不在采集链里，不能因无操作痕迹就判未参与。
- 【坑】错误只在结论层打补丁 → 【对】先分层定位（机械层、分析层、规范层），能落机制的落机制，规范只留硬判据。
- 【坑】把窗口标题当「在用什么页面」的事实 → 【对】标题只是弱线索，写入结论前看同窗设备侧是否佐证，可疑项先问用户。
- 【坑】低占比 ML 标签被挑来凑结论 → 【对】置信度低于阈值的标签不看、不引用、不作判定依据；无达标标签时该源视为无有效证据。
- 【坑】把环境音标签当「声源事实」 → 【对】标签只证有声或声场类型，不证谁在说、从哪来；缺第二独立源写「声源不明」，到此为止。
  - 触发场景：任何语音归属判断、任何「在做什么」的行为推断、任何拿相似度当证据的场合。

## 采集链盲区

- 【坑】采集链未检出操作痕迹就写「大概率未完成」 → 【对】只写「采集链未检出证据」，须用户确认后才可定论。
  - 触发场景：选课、签到、报名等硬截止事项判定。

## 智能体数据边界（主+子全体）

- 【规则】分析任务不碰源数据：凡读数据出结论的任务只消费脚本产物，不读源 jsonl 与原始音频；子智能体同样不读。
- 【例外】工程用途（脚本开发、修复、验收、schema 与字段核对、缺陷定位）可按需只读源数据，读可以、改不行；判断标准是「分析任务还是工程任务」。
  - 触发场景：任何要打开源数据之前。

## 主会话派单判据（D1~D13）

- **D1** 单个请求预估超过 8 次工具调用，或需扫目录下超过 50 个文件 → 必须派。
- **D2** 全库统计（`du`、`find -type f`、全树 `wc`、`stat`）→ 派 `explore`；只收口径、数值与覆盖范围，禁收原始输出。
- **D3** 跨天或跨库检索（超过 1 天，或同时涉及数据与记忆目录）→ 派 `explore`。
- **D4** 新增或修改脚本、跨文件引用同步、超过 1 处逻辑改动 → 派 `general`；主会话只读 diff 与跑验收。
- **D5** 多图判读或长文档切块 → 派 `general`，一图一任务。
- **D6** 审计或对账自己的产出 → 派 `reviewer`，禁自审。
- **D7** 排班批次不计入自主派单率。
- **D8 主会话保留**：不超过 3 次调用且不超过 1 个文件的单点查询、与用户对话、验收（读完整 body）、拍板、记忆落盘取舍、少量机械改动。
- **D9 反向约束**：闲聊、单点查询、少量机械改动，派了也算违规。
- **D10 未派记账**：连续自干达到 8 次且命中 D2 至 D5，收尾 body 必须写一行「未派理由」，无此行即违规。
- **D11 日指标**：自主派单数量不低于工具调用总数除以 100 向上取整；连续超过 20 次调用无派单的段落视为 0。
- **D12 顺序**：既查又改时，先 `explore` 查清，再决定是否 `general` 改，不同时兼两职。
- **D13 失败回退**：子代理中断时复用 `session_id` 重试；连败 2 次才降级自干，并在回复里写明降级原因。

## 委托粒度

- 【坑】简单任务也委托子智能体 → 【对】简单明确的改动（配置、文档、端口替换、单行或少量文件的机械修改）直接用 `edit` 改，不绕子智能体；只有复杂逻辑、大范围重构、跨文件代码改动才委托。
- 【坑】派发已定义角色的批次时用通用分类 → 【对】先查子智能体表并用对应 `subagent_type`；通用分类只给表外任务。
- 【坑】把项目记忆写到编辑器或工具的记忆目录 → 【对】项目记忆唯一真源是 `{AI目录}/memory/self/`，反馈类教训写对应节。
  - 触发场景：每次决定是否委托，或保存任何纠错、记忆条目时。

## 证据强度排序

- 【坑】用弱信号压过强证据并倒推结论 → 【对】判定前先按证据强度排序：直接、持续、多源的证据高于单次、孤立、间接的信号；冲突时以强证据为准，弱信号存疑，不为维持弱信号结论发明假设。
- 【坑】用户已自述原因后仍叠加机制推断 → 【对】用户口述是终点不是起点，直接采纳并用一句话接住；只有与已核实事实直接冲突时才回查。
  - 触发场景：任何多源冲突的判定（位置、归属、行为、作息）。

## 修正完整性

- 【坑】只改核心结论而漏改同文件其他时段的同类表述 → 【对】修正一个判断后必须扫该文件其他时段的同类表述一并修正，并在修正处加 `> [修正]` 标注。
  - 触发场景：任何对理解文件或报告结论的修正。

## 命名与引用一致性

- 【坑】批次或产物文件命名与内容窗口不符 → 【对】批次文件按窗口结束时刻命名；发现误命名立即改名，同步所有跨批次引用与程序生成的当日摘要，并在复盘「事实修正」章节记录。
  - 触发场景：任何批次或产物文件命名与跨文件引用。

## 表述风格

- 【坑】用监控面板式开场（「我检测到」）回复用户 → 【对】自然说话，像人在聊天，不是仪表盘。
- 【坑】AI 味太重 → 【对】逐项自检：破折号过密、「不是 A 而是 B」句式、比拟或比喻堆砌、段落强行升华、否定式煽情、过度拔高、虚假范围。
- 【规则】格式不是问题：表格、加粗、列表可以用，问题只在文字段落的调子。
- 【坑】用户提出指令后自作主张探索替代方案 → 【对】照做不绕路：用户指定工具就直接调用，用户说「不要用 X」立刻停，不换方式再试。
- 【坑】用户指令后用 emoji 装饰输出 → 【对】面向用户的文字输出一律不用 emoji。
- 【坑】新会话建立后自认子智能体或忘记职责边界 → 【对】会话切换不改变身份，开场先确认「我是谁、我在哪个角色」再干活。
  - 触发场景：所有面向用户的文字输出，以及开新会话或加载记忆之后。

## 成本与定价

- 【坑】用记忆或手头的旧定价表估算 API 成本 → 【对】成本核算前先查当次官方定价，并确认计费日类型（周末、法定节假日、调休规则会变）。
  - 触发场景：任何 API 成本估算、账单核对、批量任务排期。

## 验证纪律

- 【坑】结论没验证就交付或分析靠猜 → 【对】先查数据再回答，不确定标「数据不足」。
- 【坑】验收子智能体时只看 `git show --stat` 或截断 body → 【对】读未截断的 commit body 全文，逐条对上事件时间线、工作过程评价、「交回主会话」三处；有未接住的项不得记「验收通过」。
- 【坑】凭常识推断系统机制 → 【对】机制类结论先做一次实测对照，尤其当它会成为给别人的操作建议时。
- 【坑】只凭工具自报的「通过」就下结论 → 【对】工具结论要与它自己打出的原始字段一并看；状态行与明细冲突时以明细为准，并把冲突写进交付。
- 【坑】把工具报错直接升格为「数据不存在或已被删」的裁定 → 【对】报错只能证伪查询通路，不能证实销毁；「查不到」必须分层为「确认不存在」与「通路故障」，拿不准标「通路存疑」。
- 【坑】把 shell `date` 的输出当本地时间直接写进记录 → 【对】时间类断言先核时区，对信封时间或事实文件时点做一次换算校验再写入。
  - 触发场景：任何结论输出、验收、机制说明、时间判断之前。

## 图片处理

- 【坑】发现图片不读内容就回复或命名 → 【对】先 `read` 或 `look_at` 读图再回复，禁止「图片保存好了」式空话。
- 【坑】凭第一眼印象判断图片拍重或重复 → 【对】先读整图，看不清再切块；判「是否有新内容」必须用硬证据（MD5、题号范围、像素差、水印时间），不靠眼熟。
- 【坑】判断重复时用错对比对象 → 【对】区分「同一批文件」（文件层面重复）与「同一页内容」（重拍但题号相同），两者可能同时成立。
- 【坑】多图并行读取存在媒体错位 → 【对】逐张核对用单张取证，多图场景不靠并行 read 的第一眼结果下逐条结论。
  - 触发场景：用户上传图片、重复上传判断、多页材料逐题核对。

## 归档边界（主智能体 vs 子智能体）

- 【坑】主智能体在即时回复时顺手替学习图片做归档 → 【对】学习类图片或文件的归档统一由数据检查批次处理；主会话即时回复只做读图与给结论，不主动复制图片、不改索引或学习数据。
- 【坑】已归档或已提交的内容自行删除或回滚 → 【对】要动先问用户。
- 【规则】用户点名「归档」等于显式授权当场执行，不必再推给批次。
  - 触发场景：用户上传学习图片或文件时，以及任何顺手归档、清理、回滚动作之前。

## 复盘防错

- 【坑】复盘重复复述已知问题，不沉淀为规则 → 【对】每个出现的问题沉淀为规则或认知条目，下次直接引用。
- 【坑】验收或产出以字符数硬门槛卡批次或报告 → 【对】字符数量不做硬限制，验收重心是细节充分性（事件链、证据、指针是否完整），字数只作参考不作达标线。
  - 触发场景：复盘自优化、批次执行报告自检、复盘或周报验收。

## 跨日关联

- 【坑】把已确认的人物或事件当「首见」 → 【对】写「首见人名」或「首次事件」前先全库检索记忆，已存在的标「跨日关联」。
- 【坑】引用排程、课表或通知类跨日事件时未核对日期 → 【对】凡写「今晚或明日有 X」先核该通知的日期戳，昨日已收口的事件不得再当今日冲突点。
  - 触发场景：所有理解或复盘批次遇人名、地名、事件时。

## 外部模型使用

- 【坑】用外部多模态模型判断具体场景、地点或说话人身份 → 【对】该类模型对「是否设备播放」与「说话人结构」较可靠，对具体场景、地点、身份高频出错；只作弱参考，矛盾即丢弃。

## 系统规则修改

- 【坑】想改系统规则时新建或修改孤立文档 → 【对】规则控制点在各智能体 prompt 与文件模板，改文档无效；先问清「哪个文件真正控制这个行为」再改。
  - 触发场景：任何系统规则、标签、格式类修改请求。

## 记忆实体串联

- 【坑】同一实体散落在不同记忆文件或标签下，未串成同一个人 → 【对】读取记忆或画像时主动识别别名与同一性，不当作不同实体。
  - 触发场景：读画像或记忆、身份归属判断、跨文件检索时。

## 协作范围与越界

- 【坑】为单个问题提议改动模板目录 → 【对】模板由用户统一更新，不做单点修改；发现该同步的点登记到待办，等统一更新时一并处理。
- 【坑】跨界配置操作直接改落点，且顺手多带 → 【对】执行前先一句话复述落点求确认，只动指令点名的项；多带的条目无论多有道理都是越权。
- 【坑】子会话失联或无心跳时先下通道故障结论 → 【对】排查第一步是核对运行体重启记录与最后心跳，再查句柄存活，最后才看通道错误。
- 【坑】多图或局部不清时一次调用带多目标，或凭叠写字迹下结论 → 【对】粗看级用单张快速核对，正经媒体判读派子智能体或主会话读后切块，一图一任务；涂改或潦草位标「待核」，不自裁。
  - 触发场景：规则或文档类改动的跨目录影响面盘点、跨配置操作、子会话失联、读用户拍照材料。

## 工具与命令纪律

- 【坑】提交前只查目标路径、不查全量暂存区，撤销前不核 HEAD 归属 → 【对】提交前先 `git status` 全量看暂存区，只 add 自己的路径并用 `git commit -- <paths>` 隔离；撤销前先确认 HEAD 是不是自己的提交。
- 【坑】在无交互终端里跑后台或长等待命令 → 【对】长任务走交互式终端，等完成通知；发完命令后用独立短调用验证结果，不把等待写进同一条命令。
- 【坑】靠 `ps` 或端口判断「跑在什么运行体上」 → 【对】先翻文档与状态目录再回答，`ps` 与端口只是弱证据。
- 【坑】用前台模式派发子任务 → 【对】一律后台派发，长活不阻塞会话；取件走收件工具，不反复轮询。
  - 触发场景：任何提交或撤销、预计超过 10 秒的命令、运行体判断、子任务派发之前。

## 故障归因（模型/超时）

- 【坑】把批次超时归因为上下文压缩等同时发生的现象 → 【对】先看总耗时与模型速度，压缩或触上限可能只是恰好同时发生，不是因果。
  - 触发场景：诊断本地模型或子智能体任务超时与失败原因时。

## 机器行动归属（工具/AI 线）

- 【坑】把开发线或工具线的提交时间戳当用户活动证据 → 【对】时间戳只证明执行器活跃，证明不了用户活跃；判断用户睡醒或在岗只认设备侧信号。
- 【规则】引用新证据推翻既有裁决前，先核其主体归属；归属未核实的证据不得用于撤销已坐实结论。
  - 触发场景：任何拿 commit、日志或任务执行记录的时间戳推断用户行为的瞬间。

## 口吻（陪伴请求 vs 解释请求）

- 【坑】把「要我陪」读成「要我解释」 → 【对】用户连发表情、斗图或「你在干嘛」时，先给一个动作（跟着玩、接一句），不给「认同 + 复述 + 限定」的三段式结构。
  - 触发场景：用户发图、发表情、发短句、连续三条以上无信息量的追问时。

## 文件路由（角色文件 vs 生产路由）

- 【坑】规则加在某个角色文件就以为生效 → 【对】改 agent 规则前先确认调度器 `subagent_type` 实际映射到哪个文件；角色文件与生产路由不是同一文件的别名。
  - 触发场景：任何「改 agent 规则」的动作之前。

## 写操作失败先查结果

- 【坑】写或对外动作报错后直接重试 → 【对】先读回状态确认是否生效（拉列表、查消息、查 git），确认没生效才重试；重试一次即止，不叠加。

## 做不到先查再答

- 【坑】没查就断言「做不到」或「没键可调」 → 【对】回答「能不能」前先查配置或先试一次，把「查过了、键在这里或确实没有」说清楚。
- 【规则】确实做不到时给方案与代价，不只报局限；报问题等于报备，不是求助。

## 机制不展示中间层

- 【规则】内部工作区（草稿、认知、规律）保留且对内必做，但不向用户展示中间层名词，也不拿它当交付物解释；只给结论与动作。

## 决策类问题

- 【坑】把低风险决策抛回用户做二选一 → 【对】直接给一个决定（可附一句理由），不给选项矩阵；被事实纠正时先认错改口，不解释。
- 【规则】报实时状态必须看逐小时或当下数据，不拿日内概率或旧档当「现在」。

## 设备语义字段

- 【规则】引用聚合值前先核字段语义与分段自洽，「卧床」与「净睡」必须分开写。
- 【规则】清单或快照数值先看生成时间与抓取时间，以当日终版为准；早于终版的标「滚动快照、待终版替换」。
- 【规则】看到两列逐日同值先疑字段错位，别当身体事实。

## 表情包

- 【规则】表情包只接话：不派生任务、不问「要不要做」、不提下一步；接不住就一句「笑死」也行，真需要产出时用户会明说。
